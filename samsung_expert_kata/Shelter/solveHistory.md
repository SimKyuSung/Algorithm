# Shelter 풀이 기록

기준선 `SCORE < 1640`. 층 10000 개, 층마다 칸 10000 개, 칸마다 인원 1~9,
층마다 쉘터 3 개(용량 각 20000). 각 집을 어느 쉘터에 배정할지 정하는 문제.

---

## 0. 첫 파악

### sample_input

단순함. seed 만 입력.

### main.cpp 분석

1. init
   - `house[10000]` = 1~9 인원
   - `shelter[3]` = 배열에서 3 칸을 골라 0 으로 만들고 쉘터로 지정 (0~10000 위치값)
   - 각 층마다 대피소 3 개
2. 유저 함수 호출 — 0 은 대피소 3 개, 집은 1~9 명
3. 채점
   - 빈집(쉘터 칸)은 확인 안 함
   - 3 개 중 한 곳의 쉘터와 매칭
   - 한 쉘터당 최대 인원 20000 (`sum[3]`), 초과하면 감점
   - 집과 쉘터 번호를 매칭시켜 두 거리 차의 절대값을 합산 (`TOTAL`)
   - 쉘터에 매칭이 안 되어도 감점
   - 평균 점수를 구함

### 문제 분석

`house` 로 받은 1~9 의 값을 쉘터의 **위치**로 바꿔 줘야 한다.

## 1. 첫 접근 — 연속 구간 3분할 (폐기)

```
----A------B------C---
```

정해는 3 구간으로 나뉘어 구간별로 A, B, C 에 할당되는 것이라고 봤다.
왼쪽부터 A 를 꽉 채우고, 오른쪽부터 C 를 채우고, 남은 B 를 경계 조정으로 다듬는 방식.

**결과: 1828.09 (FAIL).**

### 여기서 나온 버그

- `result[]` 를 층 루프 밖에 선언해두고 "층마다 전부 덮어쓴다" 고 가정했다.
  실제로는 1 단계가 일부 인덱스만 쓰기 때문에 나머지는 이전 층 값이 남았고,
  2 단계가 그 값을 읽어 판단했다. 용량 검사를 통과했는데도 오버플로가 터진 원인.
  → **MISTAKES M-005**
- 잡은 방법: `result[]` 를 전수 재계산해서 증분으로 유지하던 `shelterCnt[]` 와 대조.
  어느 단계의 장부가 거짓말하는지 한 번에 나온다. 증분 장부 버그의 표준 진단법.

## 3. 전환점 — 비용의 단위와 용량의 단위가 다르다

채점기의 같은 루프 안 두 줄:

```c
sum[i] += org[f][c];                        // main.cpp:46 — 용량은 "사람" 단위
if (sum[i] <= 20000) TOTAL += abs(...);     // main.cpp:48 — 비용은 "집" 단위, 인원 무관
```

**9 명짜리 집과 1 명짜리 집은 비용을 똑같이 한 번씩 내는데, 자리는 9 배 차이로 먹는다.**

따라서 어떤 쉘터가 넘쳐서 집을 내보내야 할 때:

```
우선순위 = (옮겼을 때 늘어나는 거리) ÷ (그 집의 인원)      ← 작은 것부터
```

정수 나눗셈은 버려지므로 비교는 교차 곱셈으로:
`a.거리 * b.인원 < b.거리 * a.인원`

이게 "구간으로 자르면 안 되는" 이유이기도 하다. 구간 분할은 경계 근처 집들을
**인원과 무관하게** 통째로 넘기지만, 인원 큰 집을 골라 내보내면 같은 인원을
훨씬 적은 채수로 해결해서 경계 근처를 덜 벗어난다.

## 4. 순서 문제의 해소 — 중간 상태 제약 vs 최종 상태 제약

넘친 쉘터를 처리하는 순서에서 오래 막혔다.
"A 를 비우려면 B 에 자리가 있어야 하고, B 를 비우려면 C 에…" 하는 연쇄.

### 전수 나열

넘치는 조합은 `2^3 = 8` 가지. 여기서 `111` 은 배제된다:

- 층 총인원 ≈ 10000 채 × 평균 5 명 = **약 50000**
- 3 × 20000 = 60000
- 인원 분포(1~9 균등)의 집당 표준편차 2.58 → 총합의 표준편차 `2.58 × √10000 = 258`
- 50000 → 60000 은 **38 시그마**. 구조적으로 불가능

남은 7 가지를 하나씩 채웠다. 특히 `101` (A 와 C 만 넘침):

```
C > 20000, A+B+C ≤ 60000  ⇒  A+B < 40000
⇒ A 의 초과분을 B 가 다 받아도 B < 20000
⇒ 그 뒤 C 가 밀어넣어도 B = 총합 - 40000 ≤ 20000
```

### 그리고 진짜 매듭

**채점기의 용량 검사는 `assign()` 이 전부 끝난 뒤 딱 한 번 돈다** (`main.cpp:35~57`).
중간에 B 가 30000 이 되든 아무도 보지 않는다.

"받는 쪽이 넘치면 안 된다" 는 제약은 **문제가 요구한 게 아니라 스스로 만든 것**이었다.
그걸 버리는 순간 순서를 정할 일이 통째로 사라졌다.

> 이번 문제에서 제일 오래 막혔던 지점. 다음에도 반드시 확인할 것:
> **이 제약이 중간 상태에 걸리는가, 최종 상태에만 걸리는가.**

## 5. 최종 알고리즘

```
1) 각 집을 가장 가까운 쉘터에 배정한다.
2) A 와 C 의 초과분을 B 로 옮긴다.   (B 가 넘쳐도 무시)
3) B 의 초과분을 A / C 중 그 집에게 싼 쪽으로 옮긴다.

2·3 단계 공통 우선순위:  (늘어나는 거리) ÷ (인원), 작은 것부터
```

2 단계에서 목적지에 선택의 여지가 없는 게 핵심이다 — A 의 집은 B 가 항상 더 가깝고,
C 도 마찬가지다. 선택지가 하나면 결정할 게 없다.

3 단계에서 자리가 항상 충분한 근거:

```
필요한 자리 = (총합 - A' - C') - CAP
있는 자리   = (CAP - A') + (CAP - C')
차이        = 3*CAP - 총합 = 60000 - 약 50000 > 0        (A', C' 값과 무관)
```

## 6. 정렬을 쓰지 않은 이유

층이 10000 개라 층마다 merge sort 를 돌리면 시간이 안 나온다
(n log n ≈ 39000 × 3 회 × 10000 층 ≈ 10^9 급). 대신 두 성질을 쓴다.

**(a) "늘어나는 거리" 는 목록 안에서 텐트 모양이다.**
거리 함수가 구간별 1 차식이라, 한 쉘터가 담당하는 집을 칸 인덱스 순으로 늘어놓으면
양 끝이 작고 가운데가 큰 형태가 된다. 그래서 **양쪽 끝에서 작은 쪽부터 집어오면
그 자체가 오름차순 순회**다. 정렬 알고리즘이 필요 없다.

**(b) 인원은 1~9 뿐이다.**
인원별로 9 개 큐에 나눠 담으면, (a) 덕분에 각 큐가 이미 "늘어나는 거리" 오름차순이다.
같은 인원끼리는 거리 순서 = 비율 순서이므로, 매번 9 개 머리 중
비율 최소 하나만 고르면 된다 (9 방향 머지).

여기에 **예산 컷**을 더했다. 오름차순으로 담으므로, 초과분의 몇 배만 모으면
나머지는 전부 그보다 손해가 큰 집들이라 볼 필요가 없다.
배수를 2/3/4/6 으로 재보니 4 부터 점수가 평평해졌다 (1620.3 / 1618.4 / 1618.3 / 1618.3).

## 8. 다음 문제에 가져갈 것

1. **기준선이 있는 최적화 문제는 하한과 천장을 먼저 재고 시작한다.**
   내 접근의 최선이 기준선을 못 넘으면 아무리 잘 짜도 통과 못 한다.
   이번엔 구현·디버깅·최적화를 다 끝낸 뒤에야 알았다. → MISTAKES M-002 (3 회)
2. **비용의 단위와 제약의 단위가 다르면 단위당 비율로 정렬한다.**
   배낭 문제 계열의 기본형. 옷만 갈아입고 계속 나온다.
3. **제약이 중간 상태에 걸리는지, 최종 상태에만 걸리는지 구분한다.**
   중간 상태 제약이라고 착각하면 있지도 않은 순서 문제를 풀게 된다.
4. **케이스가 적으면 전수 나열이 점화식보다 빠르고 확실하다.**
   그리고 "이 케이스는 안 나온다" 는 표본이 아니라 부등식/시그마로 확정한다.
5. **반복 단위 사이에 전역 상태를 초기화한다.** → MISTAKES M-005
   증분으로 유지하는 합계는 전수 재계산과 대조해서 검증한다.
6. **검증은 20 줄 안에 끝나게 설계한다.**
   이번에 실제로 방향을 튼 검증들은 0~5 줄이었다 (채점기 `printf`, 용량검사 제거, 종이 계산).
   130 줄짜리 `optimal.cpp` 는 학습용 도구지 시험장에서 짤 것이 아니다.
