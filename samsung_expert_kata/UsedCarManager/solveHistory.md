1. 처음 접근
[age][passenger][engine][price] 형태의 리스트로 보관.
CAR cars[10][11][4000][50]; price 위치에는 대략 2.27명의 기댓값을 가지지만 여유 마진으로 50명 할당.

범위로 탐색하는 검색이라 모든 배열을 한번씩 두들기며 탐색을 하게 될것임.
값을들 정렬된 이진트리 형식으로 빠르게 찾아 가려고 했으나 저장된 갯수가 몇개 없어서 의미가 없어짐.

2. 재시도
[age][passenger][engin * 100000 + price] 형태의 리스트로 보관.
CAR cars[10][11][15,000]; price 위치에는 대략 9,090.9명의 기댓값을 가지지만 여유 마진으로 15,000명 할당. -> 테스트를 해보고 에러나면 마진을 늘림. (최대 몇까지 가는지 확인해 봐야 할듯)
저장 되는 값은 400,030,000 (약 40억 단위의 숫자, int 마진 21억, unsinged int 가능해 보이긴 함...)

효율화 하여 engin*30000+price = 120,030,000 (약 1.2억)
이렇게 할것이면 passenger도 차라리 이 로직으로 가능한지 확인. (약 13.2억)

CAR cars[10][150,000]; 연식 별로 저장.
passenger*4000*30000 + engin*30000 + price 형태의 값으로 저장.
각 연식당 100,000명의 기댓값을 가지지만 150,000명 할당 (근거 미약함, 테스트후 늘림)
정렬된 이진트리 형식으로 빠르게 검색.

3. 구현 예상-1

- buy: 이진트리 맨 마지막에 삽입하여 재위치가 올 때 까지 부모노드와 스왑
- sell: 검색하여 찾기는 쉬움. 노드 삭제가 어려워 보임. 맨 마지막 노드를 가져와서 (아마 작은값 일것임) 왼쪽값과 오른쪽 값중 작은 값과 교환 교환이 안된다면 멈추기

구현 예상중 내가 생각 한 트리 구조가 잘못됨을 인지
힙형태가 정렬이 되어 있을 것이라고 착각.

4. 구현 예상-2

내 수준에서 구현이 가능하다고 생각되는 정렬된 불균형 이진트리를 구현. 트리 deps가 길어지는 문제는 방치.

- buy: 이진트리 루트에 삽입하여 재위치가 올 때 까지 부모노드와 스왑
- sell: 검색하여 찾기는 쉬움. 이번에도 노드 삭제가 어려워 보임. 노드를 삭제후 리프노드가 있다면 위로 올려줘야함. 이때 트리 deps가 길어지는 문제를 약간이라도 해결하기 위해서 각 리프노드의 트리 사이즈를 저장하여 둘중 더 큰값으로 가져 오면 될것 으로 보임. 삭제 후 루트까지 트리 사이즈 업데이트.
- refund: 단순히 판매 한것을 가지고 있다가 역순으로 선형 검색하여(최근 것 이 저장될 확률이 높음으로) buy를 실행

refund에 대해서 생각중 sell을 할 때 필터에 걸린 것중 아무 것이나 1개 판매 한다면 안되 것 같음을 추론.
사유: 아무 것이나 판매한다면 다음 sell에서 존재하는 자동차의 갯수가 불명확해짐.

STL 사용이 불가능 함으로 노드들은 pooling 방식을 사용.

5. 트리 폐기 - 호출 빈도 비대칭

케이스당 호출 횟수를 세어보니 buy 1,000,000 / sell 약 10,000 / refund 약 100.
buy 가 sell 보다 100 배 많다. 그런데 지금까지의 설계는 전부 sell(검색) 을 빠르게 하려고
buy 에 부담을 얹는 방향이었다. 완전히 거꾸로 잡고 있었음.

원칙: 100 만 번 불리는 연산에는 아무것도 얹지 않는다.
그 대가로 만 번 불리는 연산이 일을 더 하게 만든다.
-> 트리 폐기. 버킷 배열에 그냥 뒤에 붙이는 방식(O(1))으로 전환.

6. from > to 문제 (오답노트 M-001)

채점기의 필터 호출부를 다시 읽어보니
filter_by_age(pseudo_rand() % 20, pseudo_rand() % 20)
두 인자가 독립적인 난수다. 즉 from > to 인 경우가 절반이나 발생한다.
나는 from <= to 를 무의식적으로 전제하고 설계하고 있었다.

해석이 두 가지로 갈린다.
  Case1. 뒤집힌 범위 = 아무것도 안 걸림 (네 축 중 하나만 뒤집혀도 무효 -> 유효 sell 은 6.25%)
  Case2. 뒤집힌 범위 = swap 해서 정상 범위로 취급 (모든 sell 이 유효)
없애는 비율은 두 경우가 같고 빈도만 16 배 차이난다.
(Case1 에서 유효한 경우만 보면 구간 분포가 Case2 와 동일하기 때문)

이게 틀리면 설계가 통째로 뒤집히므로 자료구조 확정 전에 먼저 판정하기로 함.

7. 구간 길이 기댓값 - 직관이 틀렸던 부분

"0~19 에서 두 개 뽑으면 평균적으로 절반쯤 덮겠지" 라고 생각했는데 틀렸다.
두 점이 서로 가까이 붙는 경우가 생각보다 많아서 실제로는 1/2 이 아니라 1/3 근처다.

test.cpp 로 실측 (30000 구간에서 두 점 거리 평균 10000 회 표본):
  Average: 10581   -> 30000 의 약 1/3

네 축을 곱하면 한 번의 sell 이 재고에서 없애는 비율은 약 1.2 ~ 1.9%.
내 원래 추측(1/2씩)대로 계산했으면 3 배 넘게 틀린 값으로 설계할 뻔했다.
작은 걸 직접 재서 직관을 교정하는 게 중요.

(덤: pseudo_rand() 는 0~32767 을 반환하는데 % 30000 을 하면 0~2767 이 두 배로 나온다.
 딱 10000 이 아니라 10581 이 나온 이유. 채점기가 차를 만들 때도 같은 편향이 있음.)

9. 삽질 두 개 (오답노트 M-003, M-004)

- 반복 속도를 올리려고 채점기의 TRY <= 10 을 TRY <= 1 로 고쳐놓고 원복을 잊음.
  1 개만 돌고 PASS 가 떠서 통과한 줄 알았다.
  채점기를 건드리는 순간 PASS 라는 신호의 의미가 사라진다.
  -> PASS 를 봤으면 git diff 로 채점기가 원본인지 먼저 확인.

- PERFORMANCE = 7020 을 보고 기준(6000) 초과라 판단, vector 를 연결 리스트로
  바꾸려 했다. 그런데 그건 make run (AddressSanitizer + -O1) 으로 잰 값이었고
  make release (-O2) 로 재니 그냥 PASS 였다.
  방향도 반대였다. 순회가 압도적으로 많은 패턴에서는 메모리가 연속인 배열이
  흩어진 노드보다 유리하다. 리스트가 이기는 건 중간 삽입/삭제가 잦고 순회가 드물 때.
  -> 시간 판단은 무조건 make release 값에서만 시작.

10. 최종 구현

자료구조: CAR inventory[20][11][1500]  ([age][passenger] 버킷 + 뒤에 붙이기)

- buy:    inventory[age][passenger-2] 뒤에 붙임. O(1)
- sell:   필터의 age / passenger 범위에 걸리는 버킷만 훑고,
          그 안에서 engine / price 를 선형 검사. 걸린 것은 주문에 복사 후 제거.
          버킷 수가 20 * 11 인데 각 축이 평균 1/3 만 걸리므로 실제로는 약 1/9 만 훑는다.
- refund: 주문 번호로 보관해둔 차들을 원래 버킷에 되돌림.
- empty(): 채점기에 init() 이 없으므로 empty() 호출이 곧 테스트케이스 종료 신호다.
           개수를 세면서 동시에 전역 상태를 초기화한다.

배열 크기 1500 의 근거: STL 버전에 버킷 최대 크기 추적을 넣어 실측한 값에 여유를 둠.
sanitizer 빌드로 10 케이스 완주해서 범위 초과가 없음을 확인.

결과: make release -> PASS, make run(ASan) -> PASS (검출 0 건)

- 교훈 정리

이 문제는 알고리즘 자체보다 문제 해석과 검증 방식이 어려웠다.
막힌 지점 네 번이 전부 "몰라서" 가 아니라 "확인을 안 해서" 였다.

1. 명시되지 않은 조건을 무의식적으로 가정 (from <= to)
2. 검증을 설계가 끝난 뒤로 미룸 (힙 정렬 착각, sell 판매 대수 오독)
3. 채점기를 고쳐놓고 원복을 잊음
4. 잘못된 빌드로 성능을 판단

느려도 맞는 기준 구현을 먼저 만들어두면
그 뒤로는 비교 대상이 생겨서 훨씬 편해진다. 다음에도 이 순서로 간다.
