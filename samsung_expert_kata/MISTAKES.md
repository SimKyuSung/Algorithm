- 새 문제를 시작하기 전에 **A. 제출 전 체크리스트** 를 먼저 훑는다.
- 디버깅으로 근본 원인이 확정되면 그 자리에서 **B. 반복 사례** 에 항목을 추가하거나 횟수를 갱신한다.
- 3 회 이상 반복된 항목은 B 의 맨 위로 올린다.

## A. 제출 전 체크리스트

문제를 풀고 나서가 아니라, **제출 버튼을 누르기 직전에** 한 줄씩 짚는다.

### 공통

- [ ] **채점기가 내 함수를 호출하는 줄을 직접 읽고, 인자에 깔고 있는 암묵적 가정을 적어봤는가** (M-001)
- [ ] **자료구조를 고르기 전에, 뒤집히면 타격이 큰 가정부터 최소 실험으로 판정했는가** (M-002)
- [ ] 배열 크기가 최악 입력을 견디는가. **그 크기를 고른 근거를 주석에 적었는가**
- [ ] 좌표 인덱스 순서가 일관적인가 (`y` 먼저, `x` 나중). 방향 배열 `dy/dx` 순서와 호출부 인자 순서가 맞는가
- [ ] 테스트케이스 사이에 전역 상태를 전부 초기화했는가 (일부만 초기화하는 게 흔한 사고)
- [ ] 격자 경계 검사를 모든 접근 경로에서 하고 있는가 (한 군데만 빠뜨려도 sanitizer 없는 시험장에선 조용히 오답)
- [ ] 재귀 깊이 / 큐 크기가 최악에서 준비한 버퍼를 넘지 않는가
- [ ] 시간을 `make release` (sanitizer 없는 `-O2`) 로 쟀는가. 디버그 빌드 시간으로 판단하지 않았는가 (M-004)
- [ ] **`git diff` 로 채점기가 원본 그대로인지 확인했는가** (M-003)
- [ ] 디버그용 출력과 `freopen` 을 지웠는가

### H2323 (청소 로봇)

- [ ] 이동 호출이 `limitMoveCnt` 를 넘지 않는가 — 넘으면 그 케이스는 **즉시 0 점**
- [ ] 벽이 아닌 칸이 하나도 남김없이 청소되었는가 — 한 칸이라도 남으면 **0 점**
- [ ] 방향이 절대/상대 중 무엇인지 헷갈리지 않았는가 (채점기가 받는 것과 내가 들고 있는 것)

### WirelessNetworkCellTower (기지국 할당)

- [ ] 기지국 셀을 덮어쓰지 않았는가 — `BIGLOSS`
- [ ] 모든 사용자 칸의 값이 `1..4` 범위 안인가 — `BIGLOSS`
- [ ] 할당된 사용자 총합이 정확히 `250,000` 인가 — 하나라도 빠지거나 생기면 `BIGLOSS`
- [ ] 기지국별 사용자 수가 용량 `67,500` 이하인가 — 초과분마다 큰 페널티

### M-001  명시되지 않은 입력 조건을 무의식적으로 가정함  (1회)

- 증상:      설계를 상당히 진행한 뒤에야 전제가 무너져 처음부터 다시 짜게 됨
- 근본 원인: 채점기가 인자를 어떻게 만들어내는지 확인하지 않고, "당연히 이럴 것" 이라는
             상식적 기대를 조건으로 깔았다. UsedCarManager 에서
             `filter_by_age(pseudo_rand() % 20, pseudo_rand() % 20)` 의 두 인자가
             독립적인 난수라 `from > to` 가 될 수 있는데, `from <= to` 를 전제로 설계함.
             문제 설명에 안 적혀 있다는 것은 "그렇지 않다" 도 가능하다는 뜻이다.
- 다음 체크: 설계 시작 전에 **채점기가 내 함수를 호출하는 줄들을 직접 훑고**,
             각 인자에 대해 내가 암묵적으로 깔고 있는 가정을 글로 하나씩 적어본다.
             적어놓고 보면 근거 없는 것이 눈에 띈다.
             확정이 안 되는 가정은 추론으로 찍지 말고, 그 가정 하나만 판정하는
             최소 실험을 돌린다 (`sample_input.txt` 의 정답과 대조).
- 발생:      UsedCarManager (2026-08-15)

### M-002  검증을 설계가 끝난 뒤로 미룸  (2회)

- 증상:      설계를 끝까지 짜고 구현에 들어간 다음에야 전제가 틀린 것을 발견하고 통째로 폐기
- 근본 원인: 불확실한 가정을 "일단 두고" 그 위에 설계를 계속 쌓았다. 검증 비용이
             가정 하나당 몇 분인데, 미룬 대가는 설계 전체를 다시 짜는 것이었다.
             두 사례 모두 아주 싸게 미리 잡을 수 있었다 —
             힙이 정렬되어 있다는 착각은 노드 5개짜리 그림 하나로,
             "sell 이 1대만 판다" 는 오독은 `sample_input.txt` 의 정답을
             sell 호출 횟수로 나누는 나눗셈 하나로 판정 가능했다.
- 다음 체크: 설계에 불확실한 가정이 보이면 **"이게 틀리면 설계가 얼마나 뒤집히나"** 를
             먼저 재고, 많이 뒤집히는 것부터 최소 실험으로 판정한 뒤 진행한다.
             실험은 전체 구현이 아니라 그 가정 하나만 재는 코드여야 한다.
             자료구조를 고르기 전에 끝내는 것이 원칙.
- 발생:      UsedCarManager (2026-08-15, 힙 정렬 착각 / sell 판매 대수 오독)

### M-003  디버깅 편의로 채점기를 고쳐놓고 원복을 잊음  (1회)

- 증상:      `PASS` 가 떴는데 실제로는 통과가 아니었다. 원인을 찾는 데 한참 걸림
- 근본 원인: 반복 속도를 올리려고 채점기의 테스트케이스 수를 `TRY <= 10` 에서
             `TRY <= 1` 로 줄여놓고 되돌리지 않았다. 케이스를 줄인 판단 자체는
             합리적이지만, 채점기를 건드리는 순간 `PASS` 라는 신호의 의미가 사라진다.
             출력만 봐서는 채점 기준이 바뀐 것을 알 수 없다는 게 핵심이다.
- 다음 체크: `PASS` 를 봤으면 **`git diff` 로 채점기가 원본인지 먼저 확인**한다.
             채점기를 줄여서 돌리고 싶으면 원본은 그대로 두고 복사본을 따로 만들어
             거기서 줄인다. 제출 전에도 같은 확인을 한 번 더.
- 발생:      UsedCarManager (2026-08-15)

### M-004  잘못된 빌드로 성능을 판단함  (1회)

- 증상:      `PERFORMANCE = 7020` 을 보고 기준(6000) 초과라 판단, 자료구조를
             `vector` 에서 연결 리스트로 바꾸려 함. 실제로는 `make release` 로 재니 통과였다
- 근본 원인: `make run` 은 AddressSanitizer 가 켜진 `-O1` 디버그 빌드다. 몇 배 느리다.
             그 시간을 실제 성능으로 읽고 자료구조 선택까지 뒤집으려 했다.
             덤으로 방향도 반대였다 — 순회가 압도적으로 많은 접근 패턴에서는
             메모리가 연속인 `vector` 가 흩어진 노드보다 유리하다.
- 다음 체크: 시간과 관련된 판단은 **무조건 `make release` 로 잰 값에서만** 시작한다.
             "느린 느낌" 으로 자료구조를 바꾸지 않는다. 바꾸기 전에
             비용의 대부분이 실제로 어디서 나는지부터 측정한다.
- 발생:      UsedCarManager (2026-08-15)
